\begin{abstract}
We build GEAR-RCA, a Graph-Guided Episodic Recall Agent for Fintech-Infrastructure Root-Cause Analysis,
combining three components prior work has only combined in pairs: a real code-dependency graph (1{,}294 nodes,
static AST parsing over the actual service codebase) queried live as a tool rather than a fixed ranking; a
tool-calling LLM agent investigating live logs, traces, and infrastructure health, with structural enforcement
replacing prompted-but-ignored instructions; and a three-tier episodic memory (known-issues note, leave-one-out
case recall, per-fault-type strategy distillation) layered on top. All 97 confirmed incidents used for scoring
come from faults triggered against a live, running system and diagnosed by an agent issuing live queries against
that same still-running system, not a static telemetry snapshot captured in advance the way every close prior
system, including GALA+, is evaluated. We are not aware of a prior RCA benchmark built and investigated this
way. The ablation is the paper's central result: across the full 97-case benchmark, the memory-enabled agent
reaches 78.4\% literal / 83.5\% fair-credit AC@1, a +12.4 / +9.3 point gain over the same agent with memory
disabled; on 11 incidents where the previously evaluated methods scored 0\%, memory-enabled reaches 81.8\%
fair-credit against 72.7\% memory-disabled. A McNemar's test on the full paired 97-case result (19 wins to 10
losses) gives $p=0.136$, a genuine, disclosed effect that has not yet reached significance at this sample size.
\texttt{REDIS\_OUTAGE} remains at 0\% without a distilled strategy, indicating memory's benefit is fault-type
dependent rather than uniform. We also disclose two genuine data-integrity bugs found and fixed mid-study as part
of the method, not buried as footnotes, and validate GEAR-RCA externally on RCAEval, a published benchmark,
reaching 93.3\% AC@1 across all six RE2 fault types on TrainTicket ($n=90$).
\end{abstract}

\section{Introduction}

Root-cause analysis (RCA) in microservice systems has moved from purely statistical and graph-theoretic methods
toward large language model (LLM) agents that reason over logs, traces, and metrics using tool calls. A parallel
line of work has begun equipping such agents with persistent memory across incidents, on the premise that a
system which has diagnosed a fault before should not have to rediscover it from scratch. Both directions are
active in 2026, separately: graph-guided LLM investigation without memory~\cite{gala}, and memory-augmented LLM
investigation without an explicit code-dependency graph~\cite{amerrcl,opsmem}.

We combine both directions in GEAR-RCA, and we push into a domain the closest prior work does not touch:
payment processing, where a root cause is frequently not an infrastructure failure but a \emph{business-domain
state fact}, such as an anti-money-laundering (AML) sanctions hold or an idempotency-key collision, that no
purely infrastructure-telemetry method is built to recall. We built the system incrementally, testing each
component in isolation before combining them. We therefore evaluate memory through a controlled ablation
(memory enabled vs.\ disabled, everything else held fixed): the controlled ablation measures whether and to
what extent memory contributes to RCA performance, which is exactly what the rest of this paper reports.

Concretely, the system we built and evaluate has three layers, each doing a distinct job rather than
duplicating the others:
\label{sec:intro-arch}

\begin{itemize}
\item \textbf{Graph.} An actual code-dependency graph, AST-extracted, queried live mid-investigation rather than
a ranking precomputed once and fixed (Section~\ref{sec:system}).
\item \textbf{LLM agent.} A tool-calling loop over logs, traces, and infrastructure health, with structural
enforcement (Section~\ref{sec:enforcement}) so a mandatory tool call cannot be skipped under budget pressure, a
failure mode prompting alone does not prevent.
\item \textbf{Memory.} A three-tier episodic memory (Section~\ref{sec:system}) layered on the graph-guided loop:
a static known-issues note, leave-one-out case recall, and per-fault-type strategy distillation from both
successes and failures.
\end{itemize}

The central empirical question this paper answers is what the memory layer adds once the graph and the
tool-using LLM are already in place and held fixed. It is not whether an LLM agent can do RCA at all, and not
whether a graph helps a memory-free agent; both questions are addressed separately by prior work
(Section~\ref{sec:related}).

Our contributions: (1) a working, tool-using RCA agent evaluated against 97 confirmed incidents from genuine fault
injections on a live 8-service payments stack -- we are not aware of prior RCA-agent benchmarks built entirely
from faults triggered against a running system, with ground truth taken from the trigger itself and confirmed by
an independent health-witness process; (2) a three-tier episodic memory system, its strategy-distillation tier
following ReasoningBank's schema~\cite{reasoningbank}, applied for the first time to business-domain RCA rather
than web-agent or software-engineering tasks; (3) a controlled ablation isolating memory's measured,
non-uniform contribution, disclosed alongside its statistical limits; and (4) two disclosed methodological
findings, a memory-persistence bug that silently dropped 27 of 28 completed investigations and a memory
leave-one-out leakage bug.

\section{Related Work}
\label{sec:related}

\subsection{Agent memory: a three-stage taxonomy}

A 2026 ACL Findings survey~\cite{survey2026} organizes LLM agent memory into three evolutionary stages
(\emph{storage}, \emph{reflection}, \emph{experience}) and six memory \emph{types} that cut across them:
in-context working, external episodic, retrieval-based semantic, reflective, experience/reasoning, and
parametric (neural, test-time-updated). Our system spans three: external episodic memory
(Section~\ref{sec:system}, Tier 2), experience/reasoning memory (Tier 3), and the in-context working memory
every tool-using agent has by construction. Tier 2's full-text case recall follows the retrieve-and-reuse
pattern case-based-reasoning surveys of LLM agents identify as dominant for episodic memory~\cite{cbrsurvey},
and building episodic memory at all follows the position that it is a missing, not optional, piece of
long-term LLM agents~\cite{episodicposition}. We do not implement reflective memory~\cite{rmm} or parametric
memory (Section~\ref{sec:limitations}).

\subsection{Closest prior systems}

Table~\ref{tab:related} summarizes the closest 2026 systems, found through a literature search covering the
full intersection of agent memory, tool-using agents, and RCA/AIOps. Every close competitor is infrastructure-
or telemetry-scoped; none targets a root cause that is a business-domain fact rather than a service failure.
GALA+~\cite{gala} (graph-guided, memory-free) and AMER-RCL~\cite{amerrcl} / OpsMem~\cite{opsmem}
(memory-augmented, largely graph-free) are architecturally complementary but none combine graph-guided
exploration, episodic memory, and structural tool-call enforcement in one system. Procedural-compliance
work~\cite{agentltl} independently identifies the exact failure mode we hand-patched
(Section~\ref{sec:enforcement}), an LLM agent ignoring a ``mandatory'' instruction under budget pressure, but
has no memory dimension.

\subsection{RCA outside the LLM-agent literature}

A separate, older line of RCA work never involves an LLM agent and is post-failure, non-memory by construction
(CIRCA~\cite{circa}, CCLH~\cite{cclh}, Lin \textit{et al.}~\cite{fastdim}, AnoMod~\cite{anomod}). All four are
complementary evidence that RCA-as-localization is well studied, but none asks what happens when the same agent
investigates the same fault twice. Two further papers motivate treating payments as its own domain without building the
agent that recalls a past incident: Narayanan~\cite{hiddenfailuremodes} catalogs payment-specific failure modes
descriptively; Porcelli~\cite{tips} models ISO 20022 inter-message timing but stops at localization.

\section{System}
\label{sec:system}

GEAR-RCA consists of the three layers introduced in
Section~\ref{sec:intro-arch}: an actual code-dependency graph
queried live rather than precomputed, an LLM tool-calling loop that drives the investigation, and a three-tier
memory layered on top. This section describes each in the order the agent actually uses them: the LLM loop and
its tools (including the graph) first, then memory. Figure~\ref{fig:architecture} shows how the three layers
connect: the agent loop queries the live payments platform through seven tools, structural enforcement gates
which tool calls the loop is allowed to skip, and the three memory tiers feed the loop's system prompt and
recall tool rather than sitting outside it.

\begin{figure*}[t]
\centering
\includegraphics[width=0.85\textwidth]{gear_rca_architecture.png}
\caption{GEAR-RCA architecture. The LLM tool-calling loop is the only component that talks to both the live
platform (via seven tools) and the three-tier memory (via the system prompt and the memory-recall tool);
structural enforcement guarantees required tools actually get called before an answer is accepted.}
\label{fig:architecture}
\end{figure*}

The agent is a multi-round tool-calling loop (up to 15 rounds) driving \texttt{gpt-oss-20b} via the NVIDIA NIM
API, with the seven tools shown in Figure~\ref{fig:architecture} (introduced in Section~\ref{sec:intro-arch}).
The graph tool (\texttt{query\_knowledge\_graph}) is queried mid-investigation against the specific services
implicated by the evidence gathered so far, not consulted once as a precomputed ranking, and its 1{,}294 nodes
come from static AST parsing of the actual service codebase, not a synthetic topology.
\subsection{Three-tier memory}

\textbf{Tier 1 (known issues).} A small curated list of confirmed, recurring, unrelated noise sources (one
entry: a persistent background error on the settlement service that twice misled independent investigations
before being documented). Static, not learned.

\textbf{Tier 2 (episodic case recall).} A SQLite database with full-text search (FTS5) over every past case's
actual evidence text. When the agent finds a distinctive log signature, it queries this store and receives
matching past cases with their \emph{confirmed} root causes. Queries exclude the incident currently under
test (leave-one-out), described further in Section~\ref{sec:leakage}.

\textbf{Tier 3 (distilled strategy).} Following ReasoningBank's schema~\cite{reasoningbank}, we distill each
fault type's accumulated cases, both successful and failed past investigations, explicitly labeled as such,
into one reusable strategy (title, one-sentence description, and 3--5 sentences of concrete guidance),
injected directly into the system prompt rather than offered as a callable tool. Coverage: 11 of 13 fault
types; two (insufficient case count) have none, and Section~\ref{sec:results} shows the resulting accuracy
gap is stark.

The two evidence sources beyond live telemetry, the code graph and the three memory tiers, are structured
differently (a live queryable graph vs.\ a three-stage injection pipeline) but converge on the same per-round
system prompt, mirroring the convergence already shown in Figure~\ref{fig:architecture}.

\subsection{Structural enforcement over prompted compliance}
\label{sec:enforcement}

An instruction marked ``MANDATORY'' in the system prompt was routinely ignored under tool-call budget
pressure: the model would exhaust its budget on log search and answer without ever invoking the graph-query or
memory-recall tools. We replaced the soft instruction with structural enforcement: the loop tracks whether
each required tool has actually been called, and if not, the next call is forced via the API's own
\texttt{tool\_choice} parameter rather than repeated as text.


\subsection{A log-retrieval ordering fix}
\label{sec:esv2}

A secondary engineering finding, kept separate from the memory ablation above since changing tools would
confound that comparison: the live Elasticsearch tool's most-recent-first, top-15 window could bury a cascading
failure's actual trigger event under later noise (confirmed on a genuine \texttt{DB\_TIMEOUT} case). Fetching both
earliest and latest events instead reaches \textbf{87.6\% literal / 95.9\% fair-credit AC@1 with zero
regressions} across the full 97 cases, with the residual literal/fair-credit gap concentrated entirely in
\texttt{CASSANDRA\_OUTAGE}.

\section{Benchmark and Methodology}

\subsection{Premise: why a live-injected benchmark}
\label{sec:premise}

An agent that scores well against replayed telemetry has been shown to pattern-match a fixed, already-known
record, not to investigate a system still changing while it looks. Yet benchmarks in this space replay
archived telemetry or inject faults into a small demo app (Table~\ref{tab:related}), not a system with the
scale and real business-domain state a production payments platform has. This is not a fringe practice: even a
2025 Microsoft Research causal-RCA method~\cite{idi} is evaluated on PetShop~\cite{petshop}, purely synthetic
time series with no logs, source code, or business-domain state at all. We built the platform before the
benchmark, live and under genuine traffic, so an injected fault has somewhere real to propagate.

The distinction is also how each incident is investigated: every close prior system, GALA+ included, hands its
agent a telemetry export captured once, so the same query always returns the same answer. Our agent issues its
tools against the platform while it is still processing live background traffic -- a service that crashed 40
seconds ago may still be mid-restart with no recovery log written yet, and two tool calls seconds apart can
legitimately disagree. This section covers fault triggering (\S\ref{sec:live-injection}), scoring
(\S\ref{sec:fair-credit}), and a leakage bug in memory's interaction with the benchmark (\S\ref{sec:leakage}).

\subsection{Live fault injection, not synthetic replay}
\label{sec:live-injection}

Every close prior benchmark replays synthetic telemetry or injects faults into a demo/toy application
(Table~\ref{tab:related}): GALA+ into OnlineBoutique/TrainTicket/AegisLab~\cite{gala}, RCAEval into demo apps
with pre-recorded telemetry~\cite{rcaeval}, OM-RAG against archived GitHub issues~\cite{omrag}. We built 110
gold cases from genuine faults injected against the live 8-service platform via five real trigger mechanisms:
process kill/restart; container stop/start on shared infrastructure (Redis, MongoDB, Cassandra); a crash with a
concurrent decoy-traffic burst causing genuine HTTP rejections on a non-root-cause service (an engineered
confound); duplicate payment submissions triggering actual idempotency logic; and sanctions-list-matching
payments confirmed \texttt{HELD} via the live compliance-holds endpoint. Ground truth for crash-based faults is
tautological; for the two payment-domain types, a \texttt{confirmed} flag records whether the intended effect
actually manifested. An independent health-witness process polls with no foreknowledge of the injected fault,
and a 240-second cooldown prevents cross-incident contamination. Of the 110 cases, 97 are \emph{confirmed} and
used for scoring; the remaining 13 are evidence-free by design and retained to test correct abstention.

\subsection{Fair-credit scoring}
\label{sec:fair-credit}

A prediction of the consuming service (\texttt{audit}/\texttt{settlement}) is credited correct when the gold
label is the underlying datastore (\texttt{cassandra}), since both are build-manifest-verified as the
\emph{only} services with a genuine Cassandra dependency -- naming the affected service correctly diagnoses the
real propagation without naming the datastore itself. Not extended to other datastores without equivalent
verification; literal and fair-credit accuracy are reported separately throughout.

\subsection{Leave-one-out memory exclusion}
\label{sec:leakage}

Because every gold case is seeded into the episodic memory store, a naive \texttt{recall\_similar\_past\_incidents}
would let the agent retrieve its own answer key during evaluation. We verified this leakage occurred (one case
returned as its own top match) and fixed it by excluding the current incident's own identifier from every
recall query.

\section{Experiments and Results}
\label{sec:results}

\subsection{Full benchmark, memory enabled}

Across all 97 confirmed cases, the memory-enabled agent reaches 78.4\% literal AC@1 (76/97) and 83.5\%
fair-credit AC@1 (81/97). Table~\ref{tab:byfault} breaks this down by fault type. Three fault types reach
100\%; the two fault types this benchmark has historically found hardest, \texttt{AML\_HOLD} and
\texttt{CASSANDRA\_OUTAGE}, reach 89\% and 62\% respectively, up from 0\% for every method previously tried on
this benchmark. \texttt{REDIS\_OUTAGE}$^\dagger$ (three confirmed cases) scores 0\%. This result is consistent
with a contribution from the strategy-distillation tier, although the three memory tiers were not ablated
independently.

On the 11 hardest cases, memory improves literal AC@1 from 27.3\% to 45.5\% and fair-credit AC@1 from 72.7\% to
81.8\%, gains of 18.2 and 9.1 points. The full benchmark shows the same direction, with gains of 12.4 and 9.3
points respectively. At the case level on the 11-case subset, the result is 3 wins to 2 losses with 6 ties; we
report this split rather than the aggregate alone, since a blanket ``memory always improves RCA'' claim is a
stronger statement than the data supports.

At full-benchmark scale, memory contributes +12.4 points literal (66.0\%$\to$78.4\%) and +9.3 points fair-credit
(74.2\%$\to$83.5\%) across all 97 confirmed cases, with identical tools, graph, and enforcement in both arms.
The no-memory arm's failures are informative: every \texttt{MONGODB\_OUTAGE} and every \texttt{REDIS\_OUTAGE}
case (3/3 each) missed both literal and fair-credit, two fault types with no datastore-equivalence rule to
rescue them and no distilled strategy or accumulated case history, consistent with strategy-distillation being
what memory contributes. By contrast, all three \texttt{CASSANDRA\_OUTAGE} misses in the no-memory arm still
earned fair-credit (the agent correctly named \texttt{settlement}, a genuine Cassandra-dependent consumer).

Because the 97 cases are paired (same incidents, memory on vs.\ off), we also ran the appropriate paired test
rather than reading the aggregate gap alone (19 cases flip in memory's favor, 10 against, 62 correct under both,
6 wrong under both): the paired test did not reach conventional significance (exact McNemar's, $p=0.136$), a
limitation discussed further in Section~\ref{sec:limitations} rather than letting the point-estimate gap imply
more certainty than the data supports. A direct-signal rule (search for a fault type's known decisive log
line before trusting funnel-stall inference), added before the memory system existed and gated only by fault
type, is present identically in both arms and alone corrected 4 of 5 \texttt{AML\_HOLD} misses in isolated
testing, so the ablation's measured gap is attributable specifically to the memory tiers built afterward, not
this earlier, separable fix.

\section{On External Comparison}
\label{sec:gala-comparison}

We do not headline a number against GALA+~\cite{gala}: its 74.44\%/73.33\% AC@1 comes from synthetic
infrastructure-fault demo benchmarks, a different domain and scoring convention than our business-domain-state
faults on a live platform. Placing the numbers side by side would be the apples-to-oranges comparison this
paper rejects elsewhere. The valid comparison is the in-benchmark ablation (Table~\ref{tab:ablation}), where the
memory-disabled arm removes only the memory tiers GALA+ also lacks, with everything else held fixed, though not yet
significant at $n=97$ (Section~\ref{sec:results}). Section~\ref{sec:rcaeval-validation} reports the direct
external comparison this section avoids, on a benchmark neither system was built for.

\subsection{External validation on RCAEval}
\label{sec:rcaeval-validation}

Unlike the GALA+ comparison above, RCAEval~\cite{rcaeval} (735 cases, three microservice systems, published
per-baseline AC@1 tables) offers a genuine opportunity most close prior work does not: a standard external
benchmark with a fixed, third-party ground truth and multiple published baselines evaluated identically.
TrainTicket is the only one of RCAEval's three systems with a full published per-baseline table, covering all
six of its RE2 fault types (\texttt{CPU}, \texttt{DELAY}, \texttt{MEM}, \texttt{DISK}, \texttt{SOCKET},
\texttt{LOSS}); we evaluate GEAR-RCA against every one of them, on all 90 RE2 TrainTicket cases, rather than
report only the two fault types (\texttt{CPU}, \texttt{DELAY}) with a direct analog in GEAR-RCA's own taxonomy
(\texttt{CPU\_SATURATION}, \texttt{NETWORK\_LATENCY}). Reporting only a partial subset when the full comparison
is available would itself look selective. GEAR-RCA's live-tool architecture had to be reduced for this environment:
RCAEval supplies static telemetry per case rather than a live system, so the container-health and cross-service
trace-reconstruction tools have no live equivalent and were dropped; a code graph was rebuilt via graphify from
each target system's actual source (AST-only, since semantic-extraction was unavailable in this evaluation
context).

Table~\ref{tab:rcaeval} reports AC@1 as published in RCAEval's own results tables~\cite{rcaeval} against
GEAR-RCA's actual, live-tool-agent result on the identical cases across all six fault types, not a partial
selection. GEAR-RCA exceeds both published baselines on five of six fault types, trailing only BARO on
\texttt{DISK} (BARO's own published strongest fault type). The mechanism responsible generalizes an insight
from the main benchmark rather than reimplementing either baseline: an empirical finding that raw anomaly
magnitude does not transfer across metric types (a caller's
propagated error-rate spike can numerically exceed the true cause's own latency spike) led us to a trace-based
fix -- grouping self-time by RPC operation name, which embeds the callee's identity -- that reads causal
structure directly rather than comparing magnitudes; this generalizes the established self-time-anomaly family
used by CloudDiag-style trace RCA methods, not a wholly new category of technique. As with the GALA+
comparison, we disclose the same caveats rather than let the numbers stand alone: this is a single run, not
averaged over repetitions the way RCAEval's own baselines are; the evaluation-window/timing protocol RCAEval
uses is not fully specified in its own paper, so exact protocol parity cannot be fully verified; and GEAR-RCA is
a live tool-using agent being compared against offline statistical baselines, a genuinely different method
class, the same caveat already made explicit for GALA+.

\section{Limitations}
\label{sec:limitations}

A memory-persistence bug and a leave-one-out leakage bug, both found and fixed mid-study, are disclosed as part
of the method rather than left out. The paired ablation reaches $p=0.136$ under McNemar's test. Natural
extensions include multi-run averaging, independent verification of the fair-credit rule, broader fault-type
coverage, and reflective memory~\cite{rmm}.

\section{Conclusion}

This paper makes three contributions, stated separately rather than merged into one vaguer claim of
``improvement.'' First, the benchmark itself (Section~\ref{sec:premise}): 110 faults triggered against a live
payments platform through five genuine mechanisms, ground truth confirmed independently -- we are not aware of
prior RCA-agent benchmarks built this way. Second, the controlled ablation isolating what memory buys: +12.4/+9.3
points (literal/fair-credit) across 97 cases, everything else held fixed, reported with its McNemar's
significance gap ($p=0.136$) and two disclosed bugs rather than hidden. Third, external validation on RCAEval:
across all six RE2 fault types on TrainTicket ($n=90$), GEAR-RCA reaches 93.3\% AC@1, providing evidence that
the approach transfers beyond the live payment benchmark it was built on.
