## 1. What this project is

ClearFlow-RCA is a real, live-triggered root-cause-analysis benchmark built on top of ClearFlow, a real 8-microservice payments processing system (Spring Boot/Java 21, Kafka, ActiveMQ, MongoDB/Cassandra/Redis/Elasticsearch, real SWIFT/SEPA rail logic). Faults are injected live (`live_fault_injector.py`) via real process kills, real container stops, or real business-state manipulation across 13 fault types. Ground truth is the injector's own claimed `root_service`. The eventual goal (per the user) is to publish this as a real, honest public benchmark comparing SLM vs larger-parameter model RCA performance on real incidents — not just an internal tool.

Two ground-truth populations exist:
- **`gold_cases/`** (71 cases): hand-curated via a strict blind-investigation protocol — form a hypothesis from raw evidence *before* reading the injector's claimed root, confirm or reject. Deliberately selected for clean, discoverable single-fault evidence. **Known selection bias**: not representative of the full population.
- **`output_live/incidents.csv`** (101 "clean" incidents, `injection_time >= 2026-08-29`): the full available population, no curation. This is the fair, real test set — same ground-truth standard the project's headline `payment_aware_rca` deterministic baseline (0.386–0.416 AC@1, depending on split) was scored against.

**There is no more data than these 101 incidents without a new live-injection campaign.** This is the hard ceiling this whole thread ran into.

## 2. Existing tools/infra used

- `eval_harness.py`: deterministic baselines (`payment_aware_rca`, `graph_topology_baseline`, `loudest_metric_baseline`), and existing LLM baselines (`agentic_rca_baseline` = real multi-round MCP tool-calling loop; `mcp_llm_rca_baseline`; `hybrid_llm_rca_baseline` = LLM only when deterministic topology pick is ambiguous — the pattern this thread's hybrid design is modeled on). **Read-only throughout this thread — nothing here was modified**, per explicit user instruction; all new work lives in `scratch_fused_*.py`.
- MCP server (`mcp-readonly-gateway`, port 8087): real tools — `get_payment_timeline`, `search_service_logs`, `get_service_dependencies`, `/mcp/cascade/diagnose-graphrag` (flat blast-radius graph traversal, no LLM).
- Neo4j (`build_agent_memory_graph.py`): a static, write-once dump of incidents/predictions/findings for dashboarding — **not** read/write during diagnosis. Identified as underused for real per-case memory (see §7).
- Jaeger: live and health-checked, but **never actually mined for RCA signal** — every method here reasons from ES log timestamps, not real span-level trace data. Identified as a likely-better implementation of temporal precedence (see §7).
- Models available: `openai/gpt-oss-20b` (NVIDIA API, primary test model), local Ollama `qwen3:8b` (SLM), `nvidia/nemotron-3-super-120b-a12b` (NVIDIA API, fast — 0.7s first-token), `deepseek-ai/deepseek-v4-pro-0813` (1M context, **dropped** — 230s+ consistently for a trivial single-word call, matches this project's prior pattern of dropping impractically slow models like `meta/muse-glimmer-30b`).

**Superseded 2026-09-04.** The original diagnosis below (statistical ceiling, not a missing trick) turned out to be half right: n=101 is still the hard ceiling, but the missing trick existed. `scratch_fused_hybrid_v5.py`'s deterministic funnel-stall-location override crossed McNemar p=0.0037 vs `payment_aware_rca` and p=0.0352 vs v3 (55/101=0.545). **Next real step, not yet done**: the held-out fault-family generalization test (§6) — v5's rule generalizes cleanly *within* this dataset (robust across threshold values 0-25), but it was still designed by looking at these exact 101 incidents' failure patterns. ## 5. A first-principles reframe raised mid-thread (not yet built)

Every method so far — z-scores, fracs, witness hits, funnel-stall ratios, community summaries — is a **proxy** for "something is wrong here." None of them directly encode what root cause actually *means*: the earliest point in a causal chain where an abnormal state originated, propagating outward along real dependency edges. The project's own prior history names this gap explicitly: *"a real fix would need to distinguish which service's degradation started first chronologically from which one has the most stalled payments... a genuine engineering task, not implemented."*

**Proposed (not built): temporal-causal precedence via real Jaeger trace spans** (not log-timestamp proxies). For each incident, find the real span where the anomalous delay first occurs in the actual call graph, walk causally from there. This is standard industry practice (MicroRCA-style critical-path analysis) and is specifically expected to be robust against the CONFOUND fault types (designed to fool magnitude-based reasoning, not precedence-based reasoning, since the decoy signal is downstream/later, not earlier).

**BUILT AND TESTED 2026-09-04 — negative result, closes this question.** `scratch_trace_precedence.py`: queried the raw `jaeger-span-YYYY-MM-DD` Elasticsearch indices directly (Jaeger's own Query API at :16686 silently returns zero results for anything older than ~72h — confirmed by direct probe — so this required bypassing it and hitting ES the same way the rest of this project already does for app logs). Two real, independent problems found:
1. **Data coverage: only 38/101 (37.6%) of incidents have any surviving span data at all.** `jaeger-span-2026-08-29` and `-08-30` are gone entirely (0/47 of that day's incidents coverable); `jaeger-span-2026-08-31` itself only starts at 07:33 (some earlier outage silently truncated it, consistent with this project's well-documented reboot/crash history). Any trace-based method evaluated only where data survives would repeat the exact same selection-bias problem already flagged for gold_cases vs output_live.
2. **Where data does survive, it contains zero real signal for this injector's fault types.** First filter attempt (any exception tag OR SERVER_ERROR) scored *worse* than v5 (5/38=0.132 vs v5's 13/38=0.342, McNemar p=0.0386 — significantly worse) because it was catching routine `CLIENT_ERROR`/400 noise (`fraud-scoring`'s `WebClientRequestException`, gateway's malformed-request rejections) that occurs continuously in normal traffic and, being early in the window, always won "earliest anomaly." Corrected to real server-side failures only (`outcome=SERVER_ERROR` or a genuine 5xx status): **0/38 covered incidents had ANY such span at all** — the method degenerates completely into its own fallback (identical to v5, 13/38=0.342, zero discordant pairs).

**Why**: this project's own well-established finding — crash-mechanism faults (`kill -9`) leave no self-evidence because the process dies before it can flush a log line — extends identically to spans. A killed process doesn't get to emit an error span any more than it gets to write a log line. The transfer doc's assumption that trace-based precedence would be "specifically expected to be robust" was a reasonable industry-standard prior, but didn't account for this project's specific injection mechanism. **Verdict: not worth further investment on this dataset** without a fundamentally different (non-crash) fault-injection mechanism or genuinely fresh, fully-retained trace data.
