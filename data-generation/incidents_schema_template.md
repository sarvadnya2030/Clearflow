# ClearFlow-RCA incident ground-truth schema (template — not yet populated)

This is the target schema for Module 7's fault injector output. It is
documented now so Module 5A's event format and this schema line up, but the
actual corpus should be generated BY the fault injector once Module 4's
pipeline exists (real AML-hold gate, real finality flag) — hand-writing
incidents here would just be guessing at ground truth.

## Columns

incident_id, fault_type, injection_service, injection_time, precondition,
root_cause_node, root_cause_event_id, affected_services, affected_payment_ids,
propagation_path, severity, duration_seconds, is_confounder

## Fault taxonomy (balanced, per the review — don't let generic infra faults dominate)

Generic infra: LATENCY, CPU_HOG, MEMORY_LEAK, NETWORK_LOSS, KAFKA_LAG, DB_TIMEOUT
Payment-state: AML_HOLD_RETRY_STORM, LIQUIDITY_LOCK_STUCK, IDEMPOTENCY_COLLISION_STORM, SETTLEMENT_FINALITY_VIOLATION

## Illustrative examples (hand-written, NOT generated ground truth)

### Example 1 — simple payment-state fault
```
incident_id: INC-EXAMPLE-001
fault_type: LIQUIDITY_LOCK_STUCK
injection_service: LiquidityReservationService
precondition: payment_state=ROUTED, liquidity_state=RESERVED
root_cause_node: LiquidityReservationService.release()
propagation_path: Liquidity -> Settlement -> Router -> Gateway
affected_payment_states: [liquidity_state stuck RESERVED, retry_count increasing]
severity: medium
is_confounder: false
```

### Example 2 — confounder (loudest symptom != root cause)
```
incident_id: INC-EXAMPLE-002
fault_type: DB_TIMEOUT
injection_service: SettlementService (database layer)
root_cause_node: settlement-db connection pool exhaustion
propagation_path: Settlement DB -> Settlement service timeout -> Kafka consumer lag (LOUDEST anomaly) -> Gateway latency spike
affected_payment_states: [settlement_state stuck PENDING, liquidity_state stuck RESERVED]
severity: high
is_confounder: true
note: a topology/telemetry-only RCA would likely point at Kafka (largest metric deviation); true root cause is the DB layer. This is the case class that tests whether payment-state signals avoid the loudest-symptom trap.
```

### Example 3 — AML-domain fault
```
incident_id: INC-EXAMPLE-003
fault_type: AML_HOLD_RETRY_STORM
injection_service: aml-compliance
precondition: aml_state=HOLD, retry_allowed misconfigured to true
root_cause_node: AML policy gate not respected by gateway retry logic
propagation_path: AML hold -> gateway retries -> duplicate-detection load -> Redis latency -> gateway latency
affected_payment_states: [idempotency_state DUPLICATE_DETECTED spike, retry_count climbing]
severity: high
is_confounder: false
```

## Note

Module 5A's `payment_events.csv` already gives every event a `service`,
`service_state`, and causal pointers (`parent_event_id`/`caused_by`) — the
fault injector's job is to inject an anomalous event into that same schema
(service_state=DEGRADED/FAILED at a specific node) and record the resulting
propagation as `affected_payment_ids`/`propagation_path`, so ground truth is
mechanically derived from the injection, not asserted by hand.
